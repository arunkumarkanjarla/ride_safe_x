# Existing code review (baseline as supplied)

## 1. How pages are produced

```
source/build.py
 ├─ assets()        copies site.css + mock.css → assets/, writes assets/brand.js
 ├─ architecture()  arch_a..arch_e → architecture/NN-*.html (+ images/diagrams/*.svg via archlib.fig)
 ├─ screens()       rider/rider2/screens3.R, driver/screens2.D/screens3.D, screens2.P, admin/screens2.A/screens3.A
 │                  → screenlib.build_app() → screens/<app>/<ID>-<slug>.html and screens/<app>/index.html
 ├─ flows()         flows/index.html (FLOWS, CROSS, CROSS2, CROSS3 tables in build.py)
 ├─ gallery()       images/index.html
 ├─ home()          index.html
 └─ source_copy()   skipped when the output folder is the repository root
source/shots.py     Playwright: screenshot #mock → images/screens/<app>/<ID>.png   (Linux-only paths)
```

* Output folder: `components.OUT` = env `BLUEPRINT_OUT` or the parent of `source/`.
* Every HTML file is written by `components.write()`; every page uses `components.page()`.
* Verified: running `py build.py` with Python 3.14.2 (README says 3.12) into a scratch folder reproduces all 219
  HTML/SVG/CSS/JS outputs byte-for-byte. The build is deterministic (admin mocks use a seeded `random`).
* `shots.py` / `shot.py` cannot run on this Windows machine: hard-coded `/opt/pw-browsers/chromium-1194/...` and
  `/home/claude/out/ridenova-blueprint`, and Playwright is not installed. PNGs therefore cannot be regenerated as-is.

## 2. Inline CSS and JavaScript (baseline counts)

| Finding | Count | Where |
| --- | --- | --- |
| `style="…"` attributes | 1,006 occurrences in 119 HTML files | 826 inside the 118 screen mocks, ~132 on architecture pages, 11 on `index.html`, rest on screen pages |
| `<style>` blocks | 0 | – |
| Inline `<script>` blocks | 1 | `architecture/26-fare-transparency.html` – fee calculator generated by `arch_e.py` |
| Inline event handlers (`onclick` …) | 0 | – |
| `eval()` / `new Function` | 0 | – |
| `innerHTML` | yes | the fee calculator builds table rows and bars with string concatenation + `innerHTML` |

The style attributes are generated by Python f-strings in the screen modules (`rider.py`, `rider2.py`, `driver.py`,
`admin.py`, `screens2.py`, `screens3.py`, `superlib.py`) and in `build.py` (home tiles) and `arch_e.py` (bars).
A rebuild would reintroduce them unless the generator itself changes – this is why the refactor is done in the
generator pipeline, not by editing HTML.

## 3. Interactivity and semantics of the mocks

* Mocks are **pictures made of HTML**: buttons are `<div class="btn">`, chips/list rows/options are `<span>`/`<div>`,
  icon buttons are `<span class="ib">` containing an SVG with no label.
* Admin sidebar items are `<a>` **without `href`** (not focusable, not navigable).
* Form fields are `<div class="inp"><label>…</label><div class="box">value</div></div>` – no real `<input>`; labels are
  not associated with controls.
* Bottom navigation items are `<span class="bn">`.
* There is **no JavaScript behaviour** on any screen. Navigation between screens is only possible through the spec
  panel ("Comes from" / "Goes to" links) and the previous/next pager – not from the controls in the mock.
* 118 screens, ~800 visual controls, 0 working controls.

## 4. Layout and responsiveness

* Phone mock is fixed `360×760` (`.phone`), admin mock fixed `1280×880` (`.desk`). On a 375 px phone the phone mock
  barely fits; the admin mock relies on horizontal scrolling in `.mock-holder`.
* Site pages are reasonably responsive (`.screen-layout` collapses below 980 px, grids use `auto-fill`).
* Fonts: system stack only (works offline).

## 5. Accessibility

* Good: `lang="en"`, headings per page, icons marked `aria-hidden="true"`, diagrams have `role="img"` + `aria-label`,
  thumbnails have `alt`.
* Gaps: non-semantic controls, unlabeled icon buttons, no focus styles inside mocks, no skip link, no `aria-current`
  on the active nav item, colour-only status chips in some admin tables.

## 6. Other observations

* `source/site.css` and `source/mock.css` are duplicated into `assets/` by the build (intended, keep).
* `build.py` home page builds thumbnails with inline `style` widths.
* `registry.py` is the single source of screen IDs, slugs and titles – the prototype reuses it.
* Screen specs (`purpose`, `how`, `elements`, `apis`, `events`, `data`, `to`, `edge`) are structured Python data – the
  prototype wiring and the generated screen documentation are derived from it rather than re-typed.
* The navigation graph (`to` lists) has **no broken targets**. Screens with **no incoming flow link**: R01, R53, D01,
  D21, D22, P01, A01, A27, A28 (reachable only from indexes/pager).
* Mock data is internally consistent for one ride (Ananya R., Arjun K., TS 09 EA 4521, ₹236, OTP 4827, ride
  RN-20260927-00125) – the prototype seed data reuses these values so screens and state agree.

## 7. Risks of changing the code

| Risk | Mitigation |
| --- | --- |
| Moving inline styles to classes changes visuals (specificity) | Extracted classes are generated per declaration and marked `!important` to keep inline-style precedence; visual parity checked by screenshot comparison against `D:\RideSafeX` |
| Converting `div`s to `button`/`a` changes UA styles | Zero-specificity reset (`:where(...)`) for buttons/links inside mocks; screenshot comparison |
| Regex rewriting corrupts markup | A tree parser (`source/htmltree.py`) with verified byte-exact round-trip on 163 files is used instead |
| Breaking the existing site navigation | Link checker test over every generated page |
| PNGs drift from HTML | PNGs are kept as design references; a Windows-compatible screenshot tool is provided with the tests |
